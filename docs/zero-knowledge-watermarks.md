# Zero-Knowledge Watermark Verification

Can we prove a watermark exists without revealing the secret key?

---

## The Problem

Current situation:

```
Watermark verification requires → Secret key
Secret key must stay secret    → Only authority can verify
Authority disappears           → Verification dies
```

If we could verify watermarks *without* the secret key, anyone could verify but only the authority could forge/remove.

---

## What We Want

| Operation | Who Can Do It |
|-----------|---------------|
| Embed watermark | Authority only (has secret key) |
| Remove watermark | Authority only (knows where it is) |
| **Verify watermark** | **Anyone** (via ZKP) |

This breaks the central point of failure for *verification* while keeping *embedding/removal* secure.

---

## How ZKP Could Work

### The Statement to Prove

```
"Image I contains watermark M, embedded with secret key K"
```

Without revealing K.

### The Proof

1. Authority publishes a **verification circuit** (the algorithm, not the key)
2. Authority generates a **proof** for each image:
   - Input: Image I, Key K, Message M
   - Output: Proof P
3. Anyone can verify:
   - Input: Image I, Message M, Proof P
   - Output: True/False

The verifier is convinced the watermark exists, but learns nothing about K.

## Technical Approaches

### 1. zk-SNARKs (Zero-Knowledge Succinct Non-Interactive Arguments of Knowledge)

**How it works:**
- Encode watermark extraction as an arithmetic circuit
- Generate proof that the circuit outputs "valid" for given inputs
- Proof is small (~200 bytes) and fast to verify

**Challenges:**
- Watermark extraction involves:
  - DCT transforms (floating point → must approximate in finite field)
  - Correlation with pseudorandom sequence
  - Thresholding decisions
- These are expensive to express as circuits
- Trusted setup required (or use zk-STARKs)

**Existing tools:** Circom, Groth16, PLONK

### 2. zk-STARKs (Zero-Knowledge Scalable Transparent Arguments of Knowledge)

**Advantages over SNARKs:**
- No trusted setup
- Post-quantum secure
- Faster proving for large computations

**Disadvantages:**
- Larger proofs (~100KB vs ~200 bytes)
- Newer, less tooling

**Existing tools:** StarkWare, winterfell

### 3. Commitment Scheme (Simpler Alternative)

Not true ZKP, but might be sufficient:

**At mint time:**
1. Authority extracts watermark from the image
2. Computes `commitment = hash(image_hash, watermark_message, salt)`
3. Stores commitment on-chain or Arweave

**At verification time:**
1. Anyone with the image can:
   - Compute `image_hash`
   - Check if `commitment` matches any stored commitment
2. Authority reveals `watermark_message` and `salt` to complete verification

**Problem:** Requires authority to reveal the message, doesn't work if authority is gone.

### 4. Publish Verification Key Only

Some watermarking schemes use asymmetric keys:

- **Embedding key** (private) - Used to embed watermark
- **Detection key** (public) - Used to detect watermark

If we use such a scheme:
- Publish the detection key
- Keep the embedding key secret

**Problem:**
- Detection key might enable removal attacks (know where to look)
- Not all watermarking algorithms support this

## Practical Considerations

### Circuit Complexity

Watermark extraction involves:

```
1. Load image pixels (millions of values)
2. Compute DCT blocks (floating point math)
3. Extract from specific coefficients (selected by secret key)
4. Correlate with spreading sequence (generated by secret key)
5. Threshold to get bits
6. Decode message
```

Steps 3-4 depend on the secret key. In a ZKP circuit:
- Key is a private input (hidden)
- Image is a public input
- Output is "message M was found" (public)

Estimating circuit size:
- 1024x1024 image = 1M pixels
- Each pixel in the circuit = ~10 constraints
- DCT per 8x8 block = ~1000 constraints
- Total: tens of millions of constraints

**This is large but feasible** with modern ZKP systems.

### Proof Generation Time

With current technology:
- Proving: Minutes to hours (depends on circuit size)
- Verification: Milliseconds

Could generate proofs at mint time and store on Arweave.

### On-Chain Verification

zk-SNARK proofs can be verified on-chain (Ethereum, Polygon):
- Groth16 verification costs ~200K gas
- Could verify watermark ownership in a smart contract

## Proposed Architecture

```
┌─────────────────────────────────────────────────────┐
│                     MINT TIME                        │
│                                                      │
│  1. Embed watermark (secret key)                    │
│  2. Generate ZKP proof:                             │
│     "This image contains watermark wallet:tokenId"  │
│  3. Store proof on Arweave                          │
│  4. Store proof hash on-chain                       │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│                  VERIFICATION                        │
│                                                      │
│  Anyone can:                                         │
│  1. Fetch proof from Arweave                        │
│  2. Verify proof against submitted image            │
│  3. Confirm watermark wallet:tokenId                │
│                                                      │
│  No secret key needed!                              │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│                AUTHORITY DIES                        │
│                                                      │
│  ✓ Proofs still on Arweave (permanent)             │
│  ✓ Anyone can verify existing tokens               │
│  ✗ Cannot mint new tokens (need secret key)        │
│  ✗ Cannot verify unlisted images (no proof exists) │
└─────────────────────────────────────────────────────┘
```

## Limitations

### 1. Only Pre-Generated Proofs

ZKP proves "this exact image has this watermark."

But watermarks survive transformation. A screenshot won't match the proof generated for the original.

**Possible solution:** Generate proofs for multiple versions (original, resized, compressed). But can't anticipate all transformations.

### 2. New Minting Still Centralized

ZKP helps with verification, not embedding. The authority is still needed to mint new tokens.

### 3. Proof Generation is Expensive

Generating a ZKP for image processing takes significant compute. Adds cost/time to minting.

### 4. Transformation Detection is Hard

The real power of watermarks is detecting them in *transformed* images (screenshots, crops, compression).

ZKP works on exact inputs. Proving "this transformed image came from an image that had watermark X" is much harder - requires proving the transformation relationship.

---

## Alternative: Verifiable Computation

Instead of ZKP, use verifiable computation:

1. Authority publishes the extraction algorithm (but not the key)
2. At verification time, authority runs extraction in a trusted execution environment (TEE) like Intel SGX
3. TEE attests: "I ran algorithm A on image I and found watermark M"
4. Anyone can verify the TEE attestation

**Trade-off:** Requires trusting the TEE hardware, not fully trustless.

---

## Summary

| Approach | Decentralized Verification | Handles Transforms | Complexity |
|----------|---------------------------|-------------------|------------|
| Current (secret key) | No | Yes | Low |
| zk-SNARK per image | Yes (exact match only) | No | High |
| Asymmetric keys | Yes | Yes | Medium |
| TEE attestation | Partially | Yes | Medium |

**Recommendation:**

For MVP, accept the central point of failure. Document it honestly.

For future:
1. Research asymmetric watermarking schemes (detection key ≠ embedding key)
2. Explore ZKP for exact-match verification (proofs stored on Arweave)
3. Consider TEE for transform-resistant verification

The "holy grail" - ZKP that handles arbitrary transformations - is an open research problem.
